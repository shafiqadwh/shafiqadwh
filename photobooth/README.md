# Photo Booth

บูธถ่ายรูปที่ **พิมพ์ออกมาให้แขกทันที** พร้อม QR ให้สแกนโหลดไฟล์ดิจิตอล
ขายแยกได้ หรือขายคู่กับเว็บแชร์รูปในโปรเจกต์เดียวกันนี้

## สถานะตอนนี้

**แกนประกอบแผ่นพิมพ์เสร็จแล้วและทดสอบครบ** — ส่วนกล้องกับเครื่องพิมพ์ยังไม่ได้ทำ

| ส่วน | สถานะ |
|---|---|
| ผังแผ่นพิมพ์ 4 แบบ (เต็มใบ · แถบยาว · สี่ช่อง · โพลารอยด์) | ✅ |
| เอฟเฟคแต่งภาพ 7 แบบ | ✅ |
| ธีมตามงาน 8 แบบ (รวมฮารีรายอ อีดิลฟิตรี/อีดิลอัฎฮา) | ✅ ใช้ไฟล์เดียวกับเว็บแชร์รูป |
| ชื่องาน + QR บนแผ่น รองรับไทย/มลายู/อังกฤษ/อาหรับ (RTL) | ✅ |
| หน้าจอบูธ (กล้อง นับถอยหลัง เลือกเอฟเฟค ดูแผ่น) | ✅ |
| **สองจอสัมผัส** — จอหน้าให้แขก จอหลังให้ช่างภาพ สั่งงานได้ทั้งสองจอ | ✅ |
| **รีโมทกดถ่าย** ทั้งแบบเสียบสายและบลูทูธ | ✅ ไม่ต้องลงไดรเวอร์ |
| **โหมดไม่ต้องพิมพ์** — ขึ้น QR บนจอ แขกสแกนรับไฟล์ทันที | ✅ ขายได้โดยไม่ต้องมีเครื่องพิมพ์ |
| ส่งรูปขึ้นเว็บ + หน้า `/p/<รหัส>` ที่ QR ชี้ไปหา | ✅ |
| **QR สองแบบ** — เห็นเฉพาะรูปตัวเอง หรือเห็นทั้งงาน + โหลดทั้งหมด | ✅ เลือกก่อนตั้งบูธ |
| **GIF ภาพเคลื่อนไหว** จากรูปชุดเดียวกับที่พิมพ์ + ปุ่มเดียวโหลดครบทั้งชุด | ✅ |
| เก็บรอบถ่ายลงดิสก์ + โทเคนสำหรับ QR | ✅ |
| สั่งพิมพ์ | ⚠️ โหมดแฟ้มใช้ได้ · โหมดสั่งพิมพ์จริง **ยังไม่เคยทดสอบกับเครื่องพิมพ์จริง** |
| พิมพ์บนอิงค์เจ็ท A4 (วางแผ่นกลางหน้า + เส้นตัด) | ✅ ดู [`docs/demo-setup.md`](docs/demo-setup.md) |
| **ส่งรอบที่ค้างขึ้นเว็บหลังงาน** (ปุ่มเดียวบนจอช่างภาพ) | ✅ |
| **เก็บเงินด้วย QR พร้อมเพย์** + สมุดบัญชีรายวัน | ✅ สร้าง QR ในเครื่อง ไม่ต้องต่อเน็ต · **คนกดยืนยันว่าเงินเข้า** |
| **หน้าตั้งค่าในแอป** | ✅ แก้ชื่องาน แบบแผ่น ราคา โหมดเก็บเงิน แล้วจอบูธโหลดค่าใหม่เอง |
| **กล้อง DSLR ต่อสาย** (Nikon / Canon ผ่าน gphoto2) | ✅ ลั่นชัตเตอร์จริง · **Linux เท่านั้น** และยังไม่เคยลองกับกล้องจริง |
| รันบน Windows | ✅ ทุกอย่างยกเว้นโหมดกล้อง DSLR |

## โครงสร้าง

```
photobooth/
  src/core/     ← ไม่รู้จักกล้อง เครื่องพิมพ์ หรือ Electron เลย
    paper.js       ขนาดสินค้า (4×6) กับขนาดหน้ากระดาษ (A4) — คนละเรื่องกัน
    mount.js       วางแผ่นขนาดสินค้าลงหน้ากระดาษจริง พร้อมเส้นตัด
    templates.js   ผังของแต่ละแบบ คิดจากสัดส่วนกระดาษ
    effects.js     เอฟเฟคแต่งภาพ (ปรับค่าสีล้วน ไม่มีไฟล์ภาพของใคร)
    sheet.js       ประกอบแผ่น: รูป + ชื่องาน + QR
    keys.js        ปุ่มรีโมท → การกระทำ (ตารางเดียว ใช้ทั้งหน้าจอและฝั่งหลัก)
    promptpay.js   สตริง QR พร้อมเพย์ตามมาตรฐาน EMVCo + CRC (คำนวณในเครื่องล้วน)
  src/main/     ← Electron main process — งานหนักทั้งหมดอยู่ฝั่งนี้
    main.js        หน้าต่าง + IPC + สะพานระหว่างสองจอ
    windows.js     แจกจอให้สองหน้าต่าง · มีจอเดียวได้หน้าต่างเดียว
    remote.js      ปุ่มที่ต้องยึดระดับระบบ (ปุ่มเสียงที่เดสก์ท็อปกินไปก่อน)
    settings.js    ค่าตั้ง · ค่าที่ผิดตกกลับไปค่าที่ใช้ได้ ไม่ใช่ทำให้บูธไม่ขึ้น
    session.js     หนึ่งรอบถ่าย = หนึ่งโฟลเดอร์ + โทเคน
    print.js       ตัวขับเครื่องพิมพ์ (file / system / cups) — system ใช้ได้ทุก OS
    sales.js       สมุดบัญชีรายวัน — หนึ่งบรรทัดต่อหนึ่งรอบที่ส่งมอบ
    camera.js      กล้องใหญ่ต่อสาย USB ผ่าน gphoto2 — ลั่นชัตเตอร์ ไม่ใช่ตัดเฟรมวิดีโอ
    preload.cjs    สะพานเดียวไปหาหน้าจอ
  src/renderer/ ← สองหน้าจอ (จอสัมผัส ไม่มีคีย์บอร์ด)
    index.html     จอหน้า — แขกเป็นคนดู เป็นเจ้าของกล้องและเจ้าของสถานะ
    operator.html  จอหลัง — ช่างภาพเป็นคนดู สั่งงานได้ แต่ไม่จำสถานะเอง
    setup.html     หน้าตั้งค่า — หน้าต่างแยก เปิดตอนตั้งบูธ ไม่ใช่ตอนแขกต่อแถว
  test/
```

`src/core/` รับ buffer เข้า คืน buffer ออก **ทดสอบได้ครบโดยไม่ต้องมีฮาร์ดแวร์**
ซึ่งจำเป็น เพราะเป็นชิ้นที่ผิดแล้วรู้ตอนกระดาษออกจากเครื่องพิมพ์ไปแล้ว

## ของที่ใช้ร่วมกับเว็บแชร์รูป

อยู่ที่ `../shared/` — **แหล่งเดียว ห้ามก๊อปไปไว้สองที่**

- `themes.json` / `themes.js` — สีและเอฟเฟคที่แนะนำต่อประเภทงาน
  ลูกค้าคนเดียวกันซื้อทั้งสองอย่างเป็นแพ็กคู่ ถ้าสีบนเว็บกับบนรูปที่พิมพ์ไม่เหมือนกัน
  แขกเห็นทันทีตั้งแต่แผ่นแรกที่ถือขึ้นมาเทียบกับจอ
- `text.js` — เรนเดอร์ตัวหนังสือด้วย Pango (ไทย/อาหรับถูกต้อง ฟอนต์เดินทางมากับโปรเจกต์)

## รัน

```sh
npm test                          # จากรากโปรเจกต์ รันทั้งเว็บแชร์รูปและ photo booth
node --test photobooth/test/*.test.js

cd photobooth && npm start        # เปิดบูธจริง (เต็มจอ · ใช้จอที่สองเองถ้ามี)
BOOTH_WINDOWED=1 npm start        # เปิดแบบหน้าต่าง ตอนตั้งค่า
BOOTH_OPERATOR=1 npm start        # บังคับเปิดจอช่างภาพ แม้เครื่องมีจอเดียว (ซ้อม)
```

`test/app.test.js` ขับแอปจริงทั้งตัวผ่าน Electron + กล้องจำลองของ Chromium
ยก Xvfb ขึ้นเองถ้าเครื่องไม่มีจอ — จึงรันได้ด้วย `npm test` เฉย ๆ ไม่ต้องเตรียมอะไร

## รันบน Windows (สำหรับทดสอบ)

```powershell
git clone <repo> ; cd photobooth
npm install
npm start
```

ต้องมี **Node.js 22** กับ **Git** เท่านั้น · `sharp` กับ `electron` มีไฟล์สำเร็จรูป
สำหรับ Windows อยู่แล้ว ไม่ต้องคอมไพล์อะไร

**ค่าตั้งอยู่ที่** `%APPDATA%\photobooth\booth\settings.json` (หรือกดเข้าหน้าตั้งค่าในแอป)

| | บน Windows |
|---|---|
| หน้าจอบูธ · สองจอ · รีโมทกดถ่าย | ✅ เหมือนกันทุกอย่าง |
| เว็บแคม · ประกอบแผ่น · GIF · QR พร้อมเพย์ | ✅ |
| **สั่งพิมพ์** | ✅ ต้องเลือกตัวขับ **"สั่งพิมพ์ผ่านระบบ"** ในหน้าตั้งค่า |
| ส่งรูปขึ้นเว็บ · หน้า `/p/<รหัส>` | ✅ |
| **กล้อง DSLR ต่อสาย** | ❌ **Linux เท่านั้น** — `gphoto2` ไม่มีบน Windows |

### สองข้อที่ต่างจาก Linux

**1. ตัวขับเครื่องพิมพ์ต้องเป็น "สั่งพิมพ์ผ่านระบบ"** — Windows ไม่มีคำสั่ง `lp`
ตัวขับ CUPS จึงใช้ไม่ได้เลย · โหมดนี้สั่งพิมพ์ผ่านตัวพิมพ์ของ Electron เอง
ไม่พึ่งคำสั่งของระบบปฏิบัติการ และ**เลือกเครื่องพิมพ์จากรายการที่ระบบรู้จัก**
ไม่ต้องพิมพ์ชื่อเอง (ชื่อเครื่องพิมพ์บน Windows แบบ `Canon SELPHY CP1500 (Copy 1)`
พิมพ์ผิดได้ง่ายมาก และผิดแล้วเงียบ — งานถูกส่งไปแล้วแต่ไม่มีอะไรออกมา)

**2. โหมดกล้อง DSLR ใช้ไม่ได้** — ตั้งไว้ก็จะตกกลับไปใช้เว็บแคมให้เองทุกครั้ง
(บูธไม่พัง แค่ได้ภาพจากเว็บแคมแทน) · การทดสอบบน Windows จึงครอบทุกอย่าง
**ยกเว้นคุณภาพภาพจากกล้องใหญ่** ซึ่งรอไปพิสูจน์บน Linux ทีหลังได้

> สิ่งที่สำคัญที่สุดที่ยังไม่เคยพิสูจน์คือ **การพิมพ์** — และข้อนั้นทดสอบบน Windows
> ได้เต็มที่ · เริ่มด้วยตัวขับ "เขียนลงแฟ้ม" ให้ได้แผ่นที่หน้าตาถูกต้องก่อน แล้วค่อย
> สลับเป็น "สั่งพิมพ์ผ่านระบบ" กับเครื่องพิมพ์จริง

## ค่าตั้ง

อยู่ที่ `<userData>/booth/settings.json` (macOS/Linux/Windows ตามที่ Electron กำหนด)
ตั้ง `BOOTH_USER_DATA` ชี้ไปที่อื่นได้ตอนซ้อม เพื่อไม่ให้ทับของงานจริง

### หน้าตั้งค่าในแอป

ค่าที่เปลี่ยนบ่อยหน้างานแก้ได้จากในแอปเลย ไม่ต้องเปิดไฟล์ JSON — **ชื่องาน ·
บรรทัดรอง · ธีม · แบบแผ่น · นับถอยหลัง · จำนวนใบ · โหมดส่งมอบ · เครื่องพิมพ์ ·
ทั้งชุดค่าเก็บเงิน** · ที่เหลือ (ที่อยู่เว็บ กุญแจ โหมด QR รหัสอัลบั้ม ปุ่มรีโมท)
ตั้งครั้งเดียวแล้วไม่แตะอีก จึงยังอยู่ในไฟล์ตามเดิม — ยิ่งหน้านี้สั้น ยิ่งหาสิ่งที่ต้อง
แก้เจอเร็วตอนอยู่หน้างาน · รวมถึง **เลือกว่าจะถ่ายด้วยเว็บแคมหรือกล้องใหญ่** พร้อมปุ่ม
**"ทดสอบ — ถ่ายจริงหนึ่งรูป"** ที่ตอบด้วยชื่อรุ่นที่เสียบอยู่จริง (บูธที่วางกล้องไว้สองตัว
จะได้รู้ว่าเสียบสายถูกตัวหรือเปล่า ตั้งแต่ตอนตั้งบูธ ไม่ใช่ตอนแขกคนแรกยืนอยู่)

| เปิดยังไง | |
|---|---|
| บูธสองจอ | ปุ่ม **⚙︎** มุมล่างขวาของจอช่างภาพ |
| บูธจอเดียว | **กดค้างที่ชื่องานสองวินาที** บนจอบูธ — ท่าที่แขกไม่บังเอิญทำ |

เปิดได้เฉพาะตอนอยู่หน้า **พร้อมถ่าย** เท่านั้น เพราะการบันทึกทำให้จอบูธโหลดค่าใหม่
ทันที (นั่นคือเหตุผลที่หน้านี้มีอยู่ — ไม่ต้องปิดเปิดแอป) การกดกลางรอบถ่ายจึงเท่ากับ
ทิ้งรอบของแขกที่ยืนอยู่ตรงนั้น

**ปุ่ม "ดู QR แล้วลองสแกน"** สร้าง QR จากเบอร์กับราคาที่กำลังพิมพ์อยู่ โดยยังไม่
ต้องบันทึก — เอาไว้ทำขั้นตอนที่โปรแกรมทำแทนไม่ได้: สแกนด้วยแอปธนาคารจริงก่อนเปิดขาย

ค่าที่บันทึกไม่ได้ **ถูกบอกเสมอ ไม่เงียบ** เช่นตั้งขายไว้แต่เบอร์พร้อมเพย์ใช้ไม่ได้
ระบบจะปิดการขายให้เอง (ถูกแล้ว — หน้าจ่ายเงินที่ไม่มี QR ให้สแกนคือบูธที่ค้างคาแถว)
แต่หน้านี้จะขึ้นเตือน แทนที่จะปล่อยให้เจ้าของเปิดบูธทั้งวันโดยเชื่อว่าตั้งขายไว้แล้ว

| ค่า | ความหมาย |
|---|---|
| `eventTitle` / `eventSubtitle` | ชื่องานกับบรรทัดรอง บนแถบล่างของแผ่น · **เว้นว่างทั้งคู่และปิด QR = ไม่มีแถบล่าง รูปกินเต็มแผ่นแทน** |
| `theme` | ธีมสีจาก `shared/themes.json` |
| `template` | `classic` · `strip` · `grid` · `polaroid` |
| `effects` | เอฟเฟคที่จะให้แขกเลือกหน้างาน (มากสุด 4) |
| `countdownSeconds` | 2–10 |
| `copies` | 1–4 ใบต่อการกดพิมพ์หนึ่งครั้ง |
| `qrMode` / `baseUrl` | `off` / `later` / `live` · ไม่มี `baseUrl` = ไม่มี QR ไม่ว่าตั้ง mode ไว้อย่างไร |
| `qrTarget` | `session` = แขกเห็นเฉพาะรอบของตัวเอง · `album` = เห็นทั้งงาน (ดูหัวข้อถัดไป) |
| `sale` | `{ enabled, target, price }` — เก็บเงินหน้าบูธด้วย QR พร้อมเพย์ (ดูหัวข้อถัดไป) |
| `gif` | ทำภาพเคลื่อนไหวจากรูปที่ถ่ายหรือไม่ (ค่าเริ่มต้น `true`) |
| `albumCode` | รหัสอัลบั้มของงาน · **โปรแกรมสร้างให้เอง อย่าแก้เอง** |
| `camera.source` | `webcam` (ค่าเริ่มต้น) หรือ `dslr` — ดูหัวข้อกล้อง DSLR |
| `camera.keepOnCard` | ให้กล้องเขียนสำเนาลงการ์ดของตัวเองด้วย (ค่าเริ่มต้นเปิด) |
| `printer.driver` | `file` (ค่าเริ่มต้น เขียนลงโฟลเดอร์ขาออก) · `system` (ใช้ได้ทุก OS **รวม Windows**) · `cups` (Linux/macOS) |
| `printer.name` | ชื่อเครื่องพิมพ์ · ว่าง = เครื่องเริ่มต้นของระบบ · เลือกจากรายการในหน้าตั้งค่าได้ |
| `deliver` | แขกได้รูปทางไหน: `print` · `screen` (QR บนจอ) · `both` |
| `uploadKey` | กุญแจเดียวกับ `BOOTH_KEY` ฝั่งเว็บ · ASCII อย่างน้อย 16 ตัว |
| `printPage` | `same` = กระดาษเท่าขนาดสินค้า (dye-sub) · `A4`/`A5`/`letter` = วางกลางหน้าแล้วตัดเอง |
| `operatorScreen` | `auto` (ใช้จอที่สองถ้าเสียบไว้) หรือ `off` |
| `remote.enabled` | รับปุ่มจากรีโมทหรือไม่ (ค่าเริ่มต้นรับ) |
| `remote.globalKeys` | ปุ่มที่ยอมให้ยึดทั้งเครื่อง — ว่างไว้เป็นค่าเริ่มต้น ดูหัวข้อรีโมท |

## กล้อง DSLR ต่อสาย — Nikon D7000 / Canon 700D

ตั้งจากหน้าตั้งค่า → **กล้อง → "กล้องใหญ่ต่อสาย USB"** · ต้องมี `gphoto2` บนเครื่อง
(`sudo apt install gphoto2` บน Debian/Ubuntu) และเป็นโหมดที่ใช้ได้บน **Linux เท่านั้น**

### สถาปัตยกรรม: แยกจอพรีวิวออกจากตัวถ่าย

```
เว็บแคมติดข้างเลนส์  →  ภาพสดบนจอ ให้แขกเห็นตัวเอง
กล้องใหญ่ต่อ USB     →  ตื่นเฉพาะตอนลั่นชัตเตอร์ ได้ไฟล์เต็มจากเซนเซอร์ APS-C
```

**กล้องใหญ่ไม่เปิด Live View เลยแม้แต่วินาทีเดียว** — และนั่นคือทั้งหมดที่ทำให้โหมดนี้
ใช้ได้จริงทั้งคืน · การเอา Live View มาทำภาพพรีวิว (ซึ่งเป็นสิ่งแรกที่ทุกคนคิดถึง)
ทำให้เกิดสามอย่างที่ฆ่างานได้จริง

| ปัญหาของ Live View | อาการหน้างาน |
|---|---|
| เซนเซอร์ร้อน | กล้อง **ปิด Live View เอง** → **จอบูธดำทันที** กลางคิว |
| แบตหมดเร็ว | 700D อยู่ได้ ~1–1.5 ชม. ไม่ถึงครึ่งงาน |
| HDMI ไม่ใช่ clean output | เมนูกับกรอบโฟกัสของกล้องไปโผล่บนจอที่แขกมองอยู่ |

พอกล้องนั่งเฉย ๆ ปัญหาทั้งสามข้อหายไปพร้อมกัน แบตก้อนเดียวถ่ายได้หลายร้อยรูป
และไม่ต้องซื้อทั้ง capture card และ DC coupler

### ตั้งกล้องหน้างาน

- **สวิตช์ที่เลนส์เป็น M** แล้วล็อกโฟกัสไว้ที่ระยะยืนของแขก + ติดเทปพันวงแหวน ·
  ไม่ใช่แค่เร็วกว่า — **Nikon จะไม่ยอมลั่นชัตเตอร์เลยถ้าโฟกัสไม่เข้า** ซึ่งกลายเป็น
  รอบที่ถ่ายไม่ออกโดยไม่มีใครรู้สาเหตุ
- **VR ปิด** (กล้องอยู่บนขาตั้ง เปิดไว้จะสั่นเองและกินแบต)
- **ตั้งกล้องถ่าย JPEG ขนาด M** — แผ่น 4×6 ต้องการแค่ 2.16MP ไฟล์ M เหลือเฟือ
  แต่โหลดผ่าน USB เร็วขึ้นเกือบเท่าตัว และกินแรมน้อยลงมาก
- **ไฟ LED ต่อเนื่อง ไม่ใช่แฟลช** — แฟลชต้องรอชาร์จระหว่างรูป และเว็บแคมพรีวิว
  จะเห็นแต่เงาดำถ้าไม่มีไฟค้าง
- `keepOnCard` (เปิดไว้เป็นค่าเริ่มต้น) สั่งให้กล้องเขียนลงการ์ดของตัวเองด้วย —
  **D7000 มีช่องการ์ดสองช่อง ทุกรูปที่ขายไปจึงมีสำเนาอยู่ในกล้องเสมอ** คืนนั้นถ้าคอม
  ดับหรือดิสก์เต็ม รูปของลูกค้ายังอยู่ครบ · กล้องที่ไม่รับคำสั่งนี้ยังถ่ายได้ตามปกติ

### กล้องพังแล้วบูธไม่พังตาม

หน้าจอ **เก็บเฟรมจากเว็บแคมไว้ทุกครั้งอยู่แล้ว** ตั้งแต่วินาทีที่แฟลชสว่าง ก่อนจะไปขอ
รูปจากกล้องใหญ่ · สายหลุด แบตกล้องหมด โปรแกรมอื่นจับกล้องไว้ กล้องค้าง — ทุกกรณี
จบลงที่ **แขกยังได้รูป ยังได้แผ่น และคิวยังเดิน** เสียแค่ความคมของรอบนั้นรอบเดียว
พร้อมคำเตือนบอกวิธีแก้ขึ้นบนจอช่างภาพ (ค้างไว้จนกว่าจะเริ่มรอบใหม่)

เสียบสายกลับเข้าไปแล้วใช้ได้ต่อทันที **ไม่ต้องปิดเปิดแอป**

> ⚠️ คำเตือนเรื่องกล้องขึ้นที่ **จอช่างภาพ** เท่านั้น (จอแขกไม่ควรขึ้นข้อความผิดพลาด)
> โหมดนี้จึงควรใช้กับบูธสองจอ · บูธจอเดียวยังใช้ได้ แต่ต้องดูจาก log แทน

### ⚠️ ยังไม่เคยลองกับกล้องจริง

โค้ดเขียนตามสเปกของ libgphoto2 และมีเทสต์ครอบทุกเส้นทาง **รวมถึงเส้นทางที่กล้องพัง**
ด้วยกล้องจำลอง — แต่กล้องจำลองพิสูจน์ได้แค่ว่าเราคุยกับ gphoto2 ถูกวิธี ไม่ได้พิสูจน์ว่า
D7000 ตัวจริงตอบแบบเดียวกัน

**ก่อนวันงานต้องลองจริงหนึ่งรอบ** — เสียบกล้อง เปิดหน้าตั้งค่า กด **"ทดสอบ — ถ่ายจริงหนึ่งรูป"**
ต้องขึ้นว่า "ถ่ายได้จริง: \<ชื่อรุ่น\>" แล้วถ่ายอีกหนึ่งรอบให้ได้แผ่นออกมาจริง

> ปุ่มนั้น **ลั่นชัตเตอร์จริง ไม่ใช่แค่เช็กว่าเสียบอยู่ไหม** โดยตั้งใจ · "เจอกล้อง" กับ
> "สั่งกล้องถ่ายได้" เป็นคนละคำถาม และมีกล้องจริงที่ตอบข้อแรกว่าใช่แต่ข้อสองว่าไม่ —
> **Sony SLT รุ่นเก่า** (A57/A58) ประกาศความสามารถ `Trigger Capture` ออกมาทาง USB
> ครบถ้วน แล้วล้มด้วย `PTP I/O Error` ตอนสั่งถ่ายจริง
> ([gphoto2#59](https://github.com/gphoto/gphoto2/issues/59)) · การตรวจที่ให้ความ
> มั่นใจผิด ๆ แย่กว่าไม่มีการตรวจเลย เพราะมันทำให้คนข้ามการซ้อมจริงไป

### กล้องรุ่นไหนใช้ได้บ้าง

โค้ดไม่รู้จักยี่ห้อกล้องเลย — มันสั่งผ่าน `gphoto2` ล้วน ๆ **กล้องที่ `gphoto2` สั่งถ่ายได้
ก็ใช้กับบูธได้ทันทีโดยไม่ต้องแก้โค้ด** และกล้องที่สั่งไม่ได้จะตกไปใช้เว็บแคมให้เอง

| | สถานะ |
|---|---|
| Nikon D7000 · Canon 700D (F-mount / EF) | รองรับดี — เป็นเป้าหมายหลักที่เขียนไว้ให้ |
| Sony SLT-A57 / A58 (A-mount) | **เสี่ยง** มีรายงานว่าสั่งถ่ายแล้วได้ PTP I/O Error · ต้องกดปุ่มทดสอบก่อนเชื่อ |
| Sony E-mount รุ่นใหม่ (A7 ฯลฯ) | รองรับดีกว่า A-mount รุ่นเก่ามาก |

## สองจอ + รีโมทกดถ่าย

เสียบจอสัมผัสตัวที่สองแล้วเปิดบูธ — **ไม่ต้องตั้งอะไรเพิ่ม** จอหลัก (ที่ระบบตั้งเป็น
primary) กลายเป็นจอหน้าให้แขก จออีกตัวขึ้นหน้าช่างภาพให้เอง · มีจอเดียวก็ได้
หน้าต่างเดียวเหมือนเดิม ไม่ใช่สองหน้าต่างซ้อนกัน

จอหลังเห็นภาพสดจากกล้อง (จอหน้าส่งต่อมาให้ 4 ภาพ/วินาที — **กล้องตัวหนึ่งเปิดได้
ทีละที่เดียว** จอหลังจึงเปิดเองไม่ได้), เห็นแผ่นที่ประกอบเสร็จ, รหัสของรอบนั้น,
จำนวนแผ่นที่พิมพ์ไปแล้ว และมีปุ่มสั่งงานสองปุ่ม

**สถานะมีเจ้าของที่เดียวคือจอหน้า** จอหลังส่งคำสั่งไปแล้วรอดูผลกลับมา — สองจอที่
ต่างคนต่างจำว่าตอนนี้ถึงไหนแล้ว คือสองจอที่พูดไม่ตรงกันทันทีที่มีอะไรพลาด

### ส่งรูปขึ้นเว็บหลังงาน

มุมขวาล่างของจอช่างภาพมีปุ่มบอกจำนวนรอบที่ยังไม่ได้ส่ง กดครั้งเดียวส่งขึ้นเว็บทั้งหมด
**นี่คือครึ่งหลังของ QR ที่พิมพ์ไปบนกระดาษแล้ว** — บูธอยู่ในเต็นท์ที่ไม่มีเน็ต โทเคน
ถูกจองตั้งแต่ตอนถ่าย ลิงก์บนกระดาษจึงถูกต้องตั้งแต่แรก แต่ปลายทางจะว่างอยู่จนกว่าจะ
กดปุ่มนี้ตอนกลับถึงบ้าน

- กดซ้ำได้เสมอ รอบที่ส่งสำเร็จถูกทำเครื่องหมายไว้แล้วจึงไม่ถูกส่งซ้ำ
- ล้มบางรอบไม่ทำให้ทั้งชุดหยุด · ปุ่มบอกจำนวนที่เหลือให้กดใหม่ทีหลัง
- ยังตั้ง `baseUrl`/`uploadKey` ไม่ครบ ปุ่มจะบอกเหตุ ไม่ใช่เป็นปุ่มเทา ๆ เฉย ๆ

### รีโมท

รีโมทกดชัตเตอร์ทั้งแบบเสียบสาย USB และแบบบลูทูธ (AB Shutter และรุ่นคล้ายกัน)
**ประกาศตัวกับระบบว่าเป็นคีย์บอร์ด** เสียบแล้วใช้ได้เลย ไม่ต้องลงไดรเวอร์
กดปุ่มเดียวได้ทั้งกระบวนการ เพราะปุ่มนั้นหมายถึง "ทำขั้นต่อไป" ไม่ใช่ "เริ่มถ่าย"

| ปุ่มที่รับ | ความหมาย |
|---|---|
| `Enter` `Space` `PageDown` `F5` `Num0` `VolumeUp` | ขั้นต่อไป: เริ่มถ่าย → พิมพ์ → ถ่ายรอบใหม่ |
| `PageUp` `VolumeDown` `Backspace` | ถอย: ทิ้งแผ่นนี้แล้วถ่ายใหม่ |

- กดรัวหรือรีโมทเด้งสัญญาณ ปุ่มเดิมภายใน 0.35 วินาทีถูกเมิน — **สั่งพิมพ์ซ้ำย้อนไม่ได้**
- ระหว่างนับถอยหลังและระหว่างกำลังพิมพ์ รีโมทไม่รับคำสั่ง เหมือนปุ่มบนจอที่ตายอยู่แล้ว
- ปุ่มเสียงบน Linux เดสก์ท็อปยึดไว้ก่อน หน้าต่างไม่มีวันเห็น — ถ้ารีโมทส่งปุ่มนั้น
  ให้ใส่ `"remote": { "globalKeys": ["VolumeUp", "VolumeDown"] }` เพื่อยึดระดับระบบ
  **ค่าเริ่มต้นไม่ยึดอะไรเลย** เพราะยึดไว้แปลว่าโปรแกรมอื่นบนเครื่องนั้นใช้ปุ่มนั้น
  ไม่ได้จนกว่าจะปิดบูธ

## QR สองแบบ — เลือกก่อนตั้งบูธ

**เลือกครั้งเดียวก่อนงาน เปลี่ยนกลางงานไม่ได้** เพราะแผ่นที่พิมพ์ไปแล้วอยู่ในมือแขก
ที่กลับบ้านไปแล้ว เราตามไปแก้ QR บนกระดาษไม่ได้

| | `qrTarget: "session"` (ค่าเริ่มต้น) | `qrTarget: "album"` |
|---|---|---|
| สแกนแล้วเห็น | เฉพาะรอบของตัวเอง | **ทุกรอบในงาน** โดยรอบของคนที่สแกนอยู่บนสุด |
| โหลดทั้งงานทีเดียว | ไม่ได้ | ได้ (ZIP แยกโฟลเดอร์ แผ่น / รูปดิบ) |
| QR พาไปที่ | `/p/<รหัสรอบ>` | `/b/<รหัสอัลบั้ม>/<รหัสรอบ>` |
| เหมาะกับ | งานที่แขกไม่รู้จักกัน · ลูกค้าที่ห่วงความเป็นส่วนตัว | งานครอบครัว/เพื่อน ที่อยากดูรูปกันทั้งงาน |

**ทำไม QR โหมดอัลบั้มยังพกรหัสรอบไปด้วย**: ถ้าลิงก์เหมือนกันทุกใบ แขกที่ถือกระดาษ
มาใบเดียวจะต้องไล่หารูปตัวเองในกองเป็นร้อย · ใส่รหัสรอบไปด้วยแล้ว QR ใบเดียวทำงาน
สองอย่าง โดยไม่ต้องพิมพ์อะไรเพิ่มลงบนแผ่น

- `albumCode` ถูกสร้างครั้งเดียวตอนเปิดบูธในโหมดอัลบั้ม แล้ว**ห้ามเปลี่ยน** ·
  เปลี่ยนแล้วแขกครึ่งแรกของงานจะถือกระดาษที่พาไปอัลบั้มที่ไม่มีรูปของใครเลย
- รอบที่ถ่ายในโหมด `session` **ไม่มีวันโผล่ในอัลบั้มไหนเลย** กันไว้ตั้งแต่ชั้นคิวรี
  ของเว็บ ไม่ใช่ชั้นหน้าเว็บ — เจ้าภาพเปลี่ยนโหมดกลางงานแล้วรูปช่วงก่อนหน้าหลุด
  ไปอยู่ในลิงก์ที่แจกทีหลัง คือสิ่งที่ต้องกันให้แน่น
- ลิงก์อัลบั้มโผล่ที่มุมล่างของจอช่างภาพด้วย เจ้าภาพขอดูตรงหน้าบูธได้เลย

## GIF — ของที่แขกได้กลับไปใช้จริงมากที่สุด

รูปสามใบที่พิมพ์ลงแผ่น ถูกประกอบเป็น GIF ให้อีกไฟล์หนึ่งด้วย · แผ่นกระดาษอยู่ใน
กระเป๋า แต่ GIF ถูกส่งต่อในไลน์กลุ่มครอบครัวคืนนั้นเลย

- **ใช้เอฟเฟคตัวเดียวกับที่แขกเลือกไว้บนแผ่น** — แผ่นโทนฟิล์มแต่ GIF สีสด
  คือของสองชิ้นที่ดูเหมือนมาจากคนละงาน
- เล่นแบบ **ไป-กลับ** (1→2→3→2) รอยต่อตอนวนซ้ำจึงไม่กระตุก
- กว้าง 540 px วนไม่รู้จบ · **128 สี** แทนเพดาน 256 ของ GIF — วัดกับภาพจากเว็บแคม
  จริงแล้วได้ 1062 KB → 478 KB และเข้ารหัสเร็วขึ้นสามเท่า โดยมองด้วยตาไม่เห็นความต่าง
  (ลองบีบข้ามเฟรมด้วยแล้ว เล็กกว่านี้อีกก็จริง แต่ทิ้งเงาจาง ๆ ของเฟรมก่อนไว้บนพื้นหลัง)
- ประกอบ **พร้อมกัน** กับแผ่น ไม่ใช่ต่อคิว — วัดแล้ว 2,024 → 1,101 มิลลิวินาที
  ประหยัดเกือบหนึ่งวินาทีต่อแขกหนึ่งคน
- ครอบภาพที่ **กลางเฟรม** ไม่ใช่ `attention` แบบบนแผ่น เพราะ attention ตัดคนละที่
  ในแต่ละเฟรม แล้วภาพจะกระตุกเหมือนกล้องสั่น
- แบบที่ถ่ายใบเดียว (`classic`) ไม่มี GIF และไม่ถือเป็นความผิดพลาด
- **ทำไม่สำเร็จก็ไม่ทำให้รอบถ่ายล้ม** แขกยืนรอเพื่อเอาแผ่น ไม่ใช่เพื่อของแถม

หน้าที่ QR ชี้ไปมีปุ่ม **"ดาวน์โหลดทั้งชุด (รูปทุกใบ + GIF)"** อยู่บนสุด ได้เป็น
ZIP ไฟล์เดียว — **ไม่ใช่สั่งโหลดทีละไฟล์ติด ๆ กัน** เพราะเบราว์เซอร์บนมือถือบล็อก
การดาวน์โหลดหลายไฟล์ซ้อน แขกจะได้ไฟล์แรกไฟล์เดียวแล้วเดินจากไปโดยคิดว่าครบแล้ว

## รูปมีอายุ แต่ QR บนกระดาษไม่มี

ฝั่งเว็บเก็บรูปจากบูธไว้ **7 วัน** แล้วลบ (`BOOTH_RETENTION_DAYS` ใน `.env` ของเว็บ ·
`0` = เก็บถาวร) นับจากวันที่รูป**ขึ้นระบบ** ไม่ใช่วันถ่าย เพราะบูธอัปโหลดหลังงานได้หลายวัน

**สิ่งที่ต้องไม่เกิด**: แขกสแกนหลังหมดอายุแล้วเจอหน้าเดียวกับตอนที่รูปยังไม่ขึ้นระบบ
("เก็บรหัสไว้แล้วกลับมาใหม่") เพราะเขาจะรอเก้อไปตลอด · หน้าที่ QR ชี้ไปจึงมีสามสถานะ

| สถานะ | แขกเห็น |
|---|---|
| ยังไม่อัปโหลด | "รูปยังไม่ขึ้นระบบ · เก็บรหัสไว้แล้วกลับมาใหม่" |
| อยู่ในระบบ | รูป + ปุ่มโหลด + **"รูปชุดนี้อยู่ถึง 10 กันยายน 2569"** |
| หมดอายุแล้ว | "รูปชุดนี้หมดอายุแล้ว · ลบไปเมื่อ… ลองติดต่อเจ้าภาพดู" |

ลบเฉพาะ **ไฟล์** เก็บ **ทะเบียน** ไว้ — แถวที่เหลือคือสิ่งเดียวที่ทำให้ QR บนกระดาษ
ยังตอบได้ว่าเกิดอะไรขึ้น แทนที่จะเป็นหน้าหาย

**บูธไม่ลบของตัวเอง** รอบถ่ายในเครื่องบูธยังอยู่ครบ (`sessions/`) คำแนะนำ
"ติดต่อเจ้าภาพ" บนหน้าหมดอายุจึงเป็นคำแนะนำที่ทำได้จริง ไม่ใช่คำปลอบใจ

## โหมดไม่ต้องพิมพ์ — ขายได้ก่อนซื้อเครื่องพิมพ์

ตั้ง `deliver: "screen"` พร้อม `baseUrl` และ `uploadKey` แล้วหลังถ่ายเสร็จ
บูธจะส่งรูปขึ้นเว็บทันทีและ **ขึ้น QR ใหญ่บนจอ** ให้แขกสแกนรับไฟล์ตรงนั้นเลย
ไม่ต้องมีเครื่องพิมพ์ ไม่ต้องมีกระดาษ ไม่ต้องมีหมึก

- ตั้ง `screen` ไว้แต่ยังไม่มี `baseUrl`/`uploadKey` จะถูก**บีบกลับเป็น `print` ให้เอง**
  — จอที่ขึ้น QR ที่สแกนแล้วไม่มีอะไร แย่กว่าไม่มีโหมดนั้นเลย
- เน็ตล่มตอนนั้น QR ยัง**ถูกต้อง**และยังขึ้นให้ พร้อมข้อความว่ารูปจะมาทีหลัง
  · ลิงก์ใช้ได้ตั้งแต่แรกเพราะรหัสถูกจองไว้ตั้งแต่ตอนถ่าย
- `deliver: "both"` = พิมพ์ด้วย ขึ้น QR ด้วย

## เดโมด้วยอิงค์เจ็ท

ยังไม่มี dye-sub ก็เดโมได้ — ตั้ง `printPage: "A4"` แล้วแผ่นขนาดสินค้าจะไปนั่งกลาง
หน้า A4 พร้อมเส้นตัดที่มุม **ขนาดที่ออกมาเท่าสินค้าจริง ไม่ถูกย่อ** และ A4 หนึ่งแผ่น
ใส่ได้สองใบ (แบบ `strip` = 4 แถบต่อกระดาษหนึ่งแผ่น) · ขั้นตอนตั้งเครื่องทั้งหมด
รวมถึง OS ที่แนะนำและวิธีหาชื่อเครื่องพิมพ์ อยู่ใน [`docs/demo-setup.md`](docs/demo-setup.md)

## ข้อควรรู้ที่จ่ายค่าบทเรียนไปแล้ว

1. **ไฟล์กรอบบูธถ่ายรูปที่แจกบน Instagram/X ห้ามใช้เชิงพาณิชย์** งานนี้ตั้งใจขาย
   เอฟเฟคทุกตัวจึงสร้างเองจากการปรับค่าสีล้วน ไม่มีไฟล์ภาพของใครในโปรเจกต์
2. **`.tint()` ของ sharp เป็น duotone** มันกลืนสีเดิมทิ้งทั้งหมด ไม่ใช่ "ทำให้อุ่นขึ้น"
   (พิกเซลฟ้า 120,150,200 → น้ำตาล 175,143,99) ใช้ `linear()` ต่อช่องสีแทน
3. **`stats()` ของ sharp อ่านจากภาพต้นทาง ไม่สนใจ `extract` ที่ต่อในไปป์ไลน์**
   ต้องตัดออกมาเป็นภาพใหม่ก่อนแล้วค่อยวัด
4. **ขนาด QR ที่สแกนติดวัดที่ "ขนาดโมดูล" ไม่ใช่ขนาดรวม** ที่อยู่ยาวขึ้น = โมดูลถี่ขึ้น
   ในกรอบเท่าเดิม · ตัวตัดสินจริงยังคงเป็นการเอากระดาษที่พิมพ์แล้วมาสแกนด้วยมือถือ
5. **`width` กับ `dpi` ของ sharp ไม่ได้อยู่ในหน่วยเดียวกัน** จึงไม่พึ่งการตัดบรรทัด
   ของ sharp ในงานพิมพ์ — `fitLines()` ขึ้นบรรทัดเองและวัดทุกบรรทัดจริง
6. **แถบล่างที่ไม่มีอะไรอยู่ข้างในต้องหายไป ไม่ใช่เหลือเป็นแถบขาว** ค่าเริ่มต้นของ
   บูธคือไม่มีชื่องานและไม่มี QR — เห็นตอนถ่ายหน้าจอแอปจริงครั้งแรก

## ที่ยังพิสูจน์ไม่ได้จากเครื่องพัฒนา

- **โหมด CUPS ยังไม่เคยเจอเครื่องพิมพ์จริง** เทสต์ครอบได้แค่คำสั่งที่ประกอบขึ้น
  ก่อนงานต้องตรวจชื่อสื่อของรุ่นที่ใช้จริงด้วย
  `lpoptions -p <ชื่อเครื่อง> -l | grep PageSize` — ไดรเวอร์ dye-sub บางรุ่นใช้ชื่อของตัวเอง
- **สีที่ออกจากเครื่อง dye-sub ไม่ตรงกับสีบนจอ** ต้องมีรอบปรับหน้าเครื่องจริงหนึ่งรอบ
- **เกณฑ์ขนาด QR เป็นกฎทั่วไป ไม่ใช่ค่าที่วัดจากเครื่องพิมพ์ตัวนี้** ตัวตัดสินคือ
  เอากระดาษที่พิมพ์แล้วมาสแกนด้วยมือถือจริง
- **ยังไม่เคยเจอจอที่สองจริงและรีโมทจริง** เครื่องพัฒนามีจอเดียว เทสต์สองหน้าต่าง
  จึงใช้ `BOOTH_OPERATOR=1` และจำลองปุ่มรีโมทด้วยการกดคีย์บอร์ดใส่หน้าต่าง
  (ซึ่งเป็นเส้นทางเดียวกับที่รีโมทจริงเดิน เพราะมันคือคีย์บอร์ดในสายตาระบบ)
  · **การแจกจอว่าตัวไหนเป็นจอหน้า ต้องลองกับจอสองตัวจริงหนึ่งครั้ง**
- **`globalKeys` ยังไม่เคยทดสอบกับเดสก์ท็อปจริง** ปุ่มเสียงบน GNOME/KDE อาจถูกยึด
  ไว้ก่อนจนจดไม่ได้ — บูธจะพิมพ์คำเตือนบอกว่าจดปุ่มไหนไม่สำเร็จ ไม่ใช่เงียบ

## เก็บเงินหน้าบูธด้วย QR พร้อมเพย์

สำหรับตอน **เปิดบูธเอง** — ออกงานแล้วขายเป็นรอบ หรือกางหน้าบ้านช่วงที่ไม่มีงาน
ปิดไว้เป็นค่าเริ่มต้น งานที่เจ้าภาพจ่ายค่าบูธมาแล้วแขกจึงไม่มีวันเจอหน้าจ่ายเงิน

```json
"sale": { "enabled": true, "target": "0812345678", "price": 150, "payWhen": "after" }
```

`target` ใส่ได้ทั้งเบอร์พร้อมเพย์ (`0812345678`, `081-234-5678`, `+66812345678`
ถือเป็นเบอร์เดียวกัน) เลขบัตรประชาชน/ผู้เสียภาษี 13 หลัก หรือ e-Wallet 15 หลัก ·
ตั้งไม่ครบหรือพิมพ์ผิด = ปิดการขายให้เอง ไม่ใช่บูธที่ขึ้น QR ของบัญชีมั่ว

### จ่ายตอนไหน — `payWhen`

**เลือกตามงาน ไม่ใช่ตามความชอบ** สองโหมดแก้คนละปัญหากัน

| | ขั้นตอน | เหมาะกับ |
|---|---|---|
| `after` (ค่าเริ่มต้น) | ถ่าย → ดูแผ่น → **จ่าย** → พิมพ์ | คนที่มาถ่ายเพราะตั้งใจจะซื้ออยู่แล้ว |
| `before` | **จ่าย** → ถ่าย → ดูแผ่น → พิมพ์ | งานที่คนเยอะและเข้าถึงบูธได้ฟรี |

**`after`** — แขกเห็นของก่อนจ่าย จึงไม่มีเรื่องขอเงินคืนเพราะรูปไม่ถูกใจ และถ้ากล้อง
หรือการประกอบแผ่นล้มก่อนหน้านั้น ก็ยังไม่มีใครจ่ายอะไรและกระดาษยังไม่ถูกใช้

**`before`** — ปัญหาที่โหมดนี้แก้ไม่ใช่แค่ "เสียรายได้" แต่คือ **เสียคิว**
งานโรงเรียน/งานวัด/ตลาดนัดจะมีคนแวะเข้ามาถ่ายเล่นแล้วเดินหนีตอนถึงหน้าจ่ายเงิน
ระหว่างนั้นคนที่ตั้งใจจะซื้อต้องยืนรอ · โหมดนี้ย้ายราคาไป **อยู่บนปุ่มแรกเลย**
(`จ่าย 50 บาท / แล้วถ่าย 3 รูป`) คนที่ไม่ได้ตั้งใจซื้อจึงเห็นราคาตั้งแต่ยังไม่แตะจอ
แล้วเดินผ่านไป — ตัวที่กันคิวจริง ๆ คือป้ายราคาบนปุ่ม ไม่ใช่ลำดับขั้นตอน

ในโหมด `before` โทเคนของรอบถูกจองตั้งแต่ตอนรับเงิน **ทุกบรรทัดในสมุดบัญชีจึงผูก
กับรอบถ่ายจริงเสมอ** — ลูกค้าทักมาว่า "จ่ายแล้วไม่ได้รูป" ก็ค้นเจอ · จ่ายแล้วแต่
กล้องเปิดไม่ขึ้น ให้เจ้าของบูธกด **"ไม่คิดเงิน"** ให้ถ่ายใหม่ (เงินรอบแรกยังอยู่ในสมุด
เพราะรับมาจริง)

**รอบที่ล้มหลังรับเงินไปแล้ว — ตั๋วไม่หายไปพร้อมเงิน** กล้องไม่ขึ้น ดิสก์เต็ม
สิทธิ์ไฟล์เพี้ยน เกิดได้จริงกับเครื่องที่รันด้วยแบตในเต็นท์ · บูธจะ **ถือตั๋วใบนั้นไว้**
แล้วกลับไปหน้าพร้อมถ่ายซึ่งขึ้นว่า **"จ่ายแล้ว — กดถ่ายได้เลย"** (จอช่างภาพขึ้นตรงกัน)
แก้ปัญหาแล้วกดต่อได้ทันทีโดยไม่ต้องจ่ายซ้ำ และรูปจะไปนั่งบนตั๋วใบเดิมที่ผูกกับเงิน

> **บั๊กที่วัดเจอตอนจำลอง** ก่อนหน้านี้รอบที่ล้มจะคืนโทเคนทิ้ง ทั้งที่จอบูธยังถือ
> โทเคนใบนั้นอยู่ → **ทุกรอบหลังจากนั้นล้มตามกันหมดทั้งคืน** เพราะไปประกอบลง
> โฟลเดอร์ที่ถูกลบไปแล้ว โดยที่ยังเก็บเงินได้ตามปกติทุกครั้ง · ดิสก์สะดุดวินาทีเดียว
> = บูธที่รับเงินแต่ไม่ออกของไปจนกว่าจะปิดเปิดแอปใหม่

คนที่จ่ายแล้วเดินหายไปเลย ให้กด **"ยกเลิกตั๋วที่จ่ายแล้ว"** บนจอช่างภาพ (หรือปุ่มถอย
บนรีโมท) ไม่งั้นคนถัดไปจะได้ถ่ายฟรี — การถือตั๋วไว้ต้องมาคู่กับทางปลดเสมอ

**เครื่องพิมพ์ไม่ออกหลังรับเงินไปแล้ว — เก็บซ้ำไม่ได้** กระดาษหมด ริบบิ้นหมด คิว CUPS
ค้าง สายเครื่องพิมพ์หลวม เกิดจริงทั้งหมด และเกิดตอนที่แขกจ่ายแล้วยืนรอกระดาษอยู่ตรงหน้า
· บูธจะกลับไปหน้า **ดูแผ่น** (แผ่นยังอยู่ครบ กดสั่งพิมพ์ใหม่ได้ทันทีที่แก้เสร็จ)
พร้อมขึ้นเหตุบนจอช่างภาพ **ค้างไว้จนกว่าจะเริ่มรอบใหม่**

> **บั๊กที่วัดเจอตอนจำลอง** โหมดจ่ายทีหลังเคยค้างอยู่ที่ **หน้าจ่ายเงิน** เมื่อพิมพ์ล้ม
> — ซึ่งเป็นหน้าที่ปุ่มหลักบนจอช่างภาพแปลว่า "ได้รับเงินแล้ว" · เจ้าของบูธที่กดซ้ำ
> เพราะคิดว่ากดไม่ติด จะจดเงินเข้าสมุดสองรอบจากลูกค้าคนเดียวโดยไม่มีอะไรเตือน
> ตอนนี้ระบบจำเป็น **"โทเคนของรอบที่จ่ายแล้ว"** ทุกอย่างหลังจากนั้น (พิมพ์ ถ่ายใหม่
> สั่งพิมพ์ซ้ำ) จึงไม่พาไปหน้าจ่ายเงินอีก ไม่ว่าจะล้มกลางทางตรงไหน

**จ่ายแล้วกด "ถ่ายใหม่" = ได้ถ่ายใหม่ ไม่ใช่ต้องจ่ายใหม่** รูปไม่ถูกใจแล้วขอถ่ายใหม่
เกิดแทบทุกรอบในงานที่คนถ่ายเป็นนักเรียน · ในโหมด `before` ปุ่มนี้ล้างรูปของรอบนั้นทิ้ง
แล้วกลับไปนับถอยหลังใหม่ทันที **โดยถือโทเคนใบเดิมไว้** รอบที่จ่ายแล้วจึงยังเป็นรอบเดียว
ไม่ว่าถ่ายกี่ครั้ง — ถ้าปุ่มนี้ทิ้งรอบไปพร้อมเงินที่รับมา เจ้าของบูธจะเหลือทางเลือกแค่
เถียงกับแขกหรือกด "ไม่คิดเงิน" ให้ทุกครั้งจนสมุดบัญชีเต็มไปด้วยรอบฟรีที่ไม่ได้ฟรีจริง
(ในโหมด `after` ยังไม่มีใครจ่าย ปุ่มนี้จึงทิ้งรอบไปตามเดิม)

**ปุ่มยืนยันรับเงินอยู่จอไหน**

| ติดตั้ง | ปุ่มอยู่ที่ |
|---|---|
| สองจอ (มีจอช่างภาพ) | **จอช่างภาพเท่านั้น** — จอแขกขึ้นว่า "รอเจ้าของบูธยืนยัน" |
| จอเดียว (กางหน้าบ้าน) | จอแขก — ไม่งั้นบูธค้างคาแถวโดยไม่มีอะไรให้กด |

รีโมทกดถ่ายทำหน้าที่ "ได้รับเงินแล้ว" ตอนอยู่ขั้นนี้ทั้งสองแบบ — รีโมทอยู่ในมือ
เจ้าของบูธซึ่งเป็นคนเดียวที่เห็นแอปธนาคาร · ปุ่ม **"ไม่คิดเงิน"** อยู่บนจอช่างภาพ
เท่านั้นและ **ไม่มีบนรีโมทโดยตั้งใจ** การยกเว้นค่าถ่ายต้องเป็นการกดที่ตั้งใจกด

### ⚠️ ข้อจำกัดที่ต้องรู้ก่อนใช้

**โปรแกรมไม่มีทางรู้ว่าเงินเข้าแล้วหรือยัง** QR ที่สร้างเป็นสตริงตามมาตรฐาน EMVCo
ที่คำนวณในเครื่องล้วน ๆ (ข้อดีคือใช้ได้ในเต็นท์ที่ไม่มีสัญญาณ) การตรวจว่าเงินเข้า
ต้องต่อ API ของธนาคารหรือผู้ให้บริการชำระเงิน ซึ่งต้องสมัครแยกและเป็นคนละเรื่องกัน

สิ่งที่ระบบนี้ทำคือ **จดตามที่คนกดยืนยัน** — เจ้าของบูธดูแอปธนาคารแล้วกดเอง
ตัวเลขในสมุดบัญชีจึงเป็น "ที่กดยืนยันไว้" ไม่ใช่ "ที่ธนาคารรับรอง" กระทบยอดกับ
แอปธนาคารตอนเก็บบูธเสมอ

**ก่อนเปิดขายจริงครั้งแรก: สแกน QR ด้วยแอปธนาคารของตัวเองหนึ่งครั้ง** แล้วดูว่า
ขึ้นชื่อบัญชีตัวเองกับยอดที่ถูกต้อง · เทสต์ตรวจได้แค่ว่าสตริงถูกตามมาตรฐาน
ตรวจแทนไม่ได้ว่าแอปธนาคารรับ

### สมุดบัญชี

`<userData>/booth/sales/YYYY-MM-DD.ndjson` — บรรทัดละหนึ่งรอบ

```json
{"at":"2026-09-03T14:20:11.000Z","token":"K7QX2M","amount":150,"free":false}
```

ต่อท้ายทีละบรรทัด ไม่เขียนทับทั้งไฟล์ — บูธรันด้วยแบตเตอรี่ ไฟดับกลางเขียนทับ
คือเสียยอดทั้งวัน · และก่อนต่อท้ายจะขึ้นบรรทัดใหม่ให้ถ้าไฟล์จบด้วยบรรทัดที่ขาด
เศษที่ไฟดับทิ้งไว้จึงเสียแค่บรรทัดของมันเอง ไม่ลากรอบถัดไปหายไปด้วย

รอบที่ไม่คิดเงินก็อยู่ในสมุด (`free: true`, `amount: 0`) ไม่งั้นจำนวนแผ่นที่พิมพ์
กับจำนวนรอบที่เก็บเงินจะไม่ตรงกันตอนนับกระดาษที่เหลือ

**ยอดที่ขึ้นบนจอช่างภาพคือยอด "กะนี้" ไม่ใช่ "วันนี้"** — `รับแล้ว 450 บาท · 4 รอบ (ฟรี 1)`
งานเลิกดึกข้ามเที่ยงคืนเป็นเรื่องปกติ ถ้านับตามวันปฏิทินตัวเลขจะรีเซ็ตเป็นศูนย์
ตอนเที่ยงคืนทั้งที่บูธยังเปิดอยู่ · "กะนี้" = ไล่ย้อนจากตอนนี้จนเจอช่องว่างเกิน 6 ชั่วโมง
(ไฟล์ยังแยกตามวันปฏิทินเหมือนเดิม นั่นคือบันทึกสำหรับกระทบยอดย้อนหลัง)
